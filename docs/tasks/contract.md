## 6.1.1. Решения, эндпоинты, снапшот

_Подгруппа **C1** · 3 задачи._

### CT-01 · Сквозные решения контракта

**Зависит:** —
**Объём:** перенести §3 в `contract/decisions.md` (D-01…D-18, коды ошибок, enum-ы, лимиты, события, метрики).
**AC:**
- [ ] Каждое решение имеет ID и ссылку на UC; ни одного `TBD`.
- [ ] Каталог кодов ошибок используется и в BE, и в FE (общий файл-источник).
- [ ] Матрица прав §3.3 покрывает все группы эндпоинтов.

### CT-02 · Каталог эндпоинтов и трассировка

**Зависит:** CT-01
**Объём:** §4 → `contract/endpoints.md`; сверка с Приложением A ТЗ.
**AC:**
- [ ] У каждой операции: роли, коды ошибок, идемпотентность/версия, форма ответа.
- [ ] 100% UC из Приложения A имеют хотя бы один эндпоинт (§11).

### CT-03 · Скелет OpenAPI

**Зависит:** CT-02, BE-00
**Объём:** все роутеры с полными путями, `response_model`, объявленные `responses`, тела возвращают 501; экспорт снапшота.
**AC:**
- [ ] `make openapi` даёт валидный OpenAPI 3.1, снапшот в git.
- [ ] Все операции §4 присутствуют (`oasdiff`/`spectral` без ошибок).
- [ ] 501-ответы соответствуют объявленным схемам.

## 6.1.2. Кодогенерация, mock, гейты, эволюция

_Подгруппа **C2** · 5 задач._

### CT-04 · Кодогенерация фронтенда

**Зависит:** CT-03, FE-00
**Объём:** orval (types + zod + fetch), `pnpm gen:api`, gitignore для `frontend/generated`.
**AC:**
- [ ] Генерация детерминирована и идемпотентна.
- [ ] Типы и zod-схемы покрывают все операции и request-body.
- [ ] CI падает при расхождении контракта и кода.

### CT-05 · CI-гейты контракта

**Зависит:** CT-03, CT-04
**Объём:** job `contract`: export, `git diff --exit-code`, `oasdiff breaking`, проверка кодогенерации.
**AC:**
- [ ] PR с правкой DTO без снапшота — красный.
- [ ] Breaking-изменение — красный + метка `breaking-contract`.
- [ ] Время job ≤ 3 мин.

### CT-06 · Mock-сервер

**Зависит:** CT-03
**Объём:** `mock-server.config.ts` (mock-config-server) с путями из контракта; типы данных — из `components`; примеры для всех DTO; `pnpm mock`.
**AC:**
- [ ] FE поднимается и работает без backend.
- [ ] Воспроизводимы 401/403/409/429 через `Prefer: example=`.
- [ ] Mock-режим включён в e2e-конфиг для UI-тестов.

### CT-07 · Контрактные тесты (schemathesis)

**Зависит:** CT-03, BE-03
**Объём:** прогон по всем операциям с авторизацией по ролям; whitelist известных расхождений с комментарием.
**AC:**
- [ ] Все операции проверены на соответствие схеме в CI.
- [ ] Whitelist пуст или обоснован ссылкой на задачу.

### CT-08 · Примеры и правила эволюции

**Зависит:** CT-03
**Объём:** `examples` в каждой схеме; правила breaking/deprecation в `contract/decisions.md`; PR-шаблон.
**AC:**
- [ ] Мок отдаёт осмысленные данные для каждого эндпоинта.
- [ ] Чек-лист «это breaking?» в PR-шаблоне.

### CT-09 · Stateful mock API

**Зависит:** CT-03, CT-06
**Объём:** `mock/` (FastAPI, in-memory, без БД): auth (register/login/refresh), бронь и отмена, верификация + решение, тикет + смена статуса, закрытие аренды, «доставка» уведомлений в лог; сценарии ошибок через `X-Mock-Scenario`; `POST /__mock/reset`.
**AC:**
- [ ] Сценарий «регистрация → верификация → бронь → тикет» проходит на моке без БД и backend.
- [ ] Ответы соответствуют `contract/openapi.json` (schemathesis прогоняется и по моку).
- [ ] Состояние детерминированно сбрасывается `/__mock/reset`; e2e стартует с чистого мока.
- [ ] Режим мока — `pnpm dev:full`; переключение на backend — переменная окружения `MOCK_ORIGIN`/прокси.
