# Аналитика аренды

Раздел доступен сотрудникам с правом `analytics.view`. Запросы и выгрузка ограничены текущей
организацией. Все ответы возвращают `Cache-Control: no-store`.

## Период и метрики

Параметры `from` и `to` — даты и время с часовым смещением. Отчёт охватывает полуоткрытый
интервал `[from, to)` длительностью до 366 суток. Для дневной группировки границы вычисляются
по календарю организации, поэтому дни перехода на летнее или зимнее время могут длиться 23
или 25 часов. Первый и последний дни учитываются в пределах заданного интервала.

| Поле | Расчёт |
| --- | --- |
| `revenue_minor` | Сумма сохранённых цен активных, просроченных и завершённых аренд, начавшихся в периоде |
| `rentals_count` | Все аренды, начавшиеся в периоде, включая отменённые |
| `cancelled_count` | Отменённые аренды из числа начавшихся в периоде |
| `overdue_count` | Просроченные аренды из числа начавшихся в периоде |
| `avg_rental_minor` | Выручка, делённая на число неотменённых аренд. Округляется до целой минорной единицы |
| `utilization_pct` | Объединённое время активных, просроченных и завершённых аренд по лотам, обрезанное по границам окна, делится на длительность окна, умноженную на число текущих неархивных лотов. Округляется до 0,1 процентного пункта |

Аренды, начавшиеся раньше окна, участвуют в расчёте загрузки за время пересечения. Пересечения
аренд одного лота считаются один раз. Забронированные и отменённые аренды, блокировки и окна
обслуживания в загрузку не включаются. Архивные лоты сохраняют финансовую историю.
При нулевом знаменателе значение метрики равно нулю.

## Операции

| GET под `/api/v1/admin/analytics` | Ответ |
| --- | --- |
| `/summary` | Итоговые показатели |
| `/revenue` | `group_by=category`, `lot` или `day`; агрегаты с выручкой и загрузкой |
| `/lots/{lot_id}` | Название лота, показатели, дневные строки и страницы аренд по `limit` (1–100) и `offset` |
| `/utilization` | Та же форма агрегатов, по умолчанию по лотам |
| `/compare` | `compare_from` и `compare_to` задают второй период. `delta` содержит абсолютные разницы `current - previous`, для загрузки в процентных пунктах |
| `/export` | `report=rentals&format=csv`; строки всех аренд, начавшихся в окне |

Дневные строки идут по порядку с нулями за дни без аренд. Группировка по категории или лоту
использует их текущие названия. Существующий лот без аренд возвращает нули и пустой список.
Недоступный лот возвращает `404`.

В `summary`, `revenue`, `utilization` и `compare` можно передать `category_id`. В этом случае
финансовые показатели и доступное время ограничены лотами выбранной категории. Сравнение
применяет один фильтр к обоим периодам.

## CSV

Файл содержит UTF‑8 BOM, заголовки на русском и разделитель `;`. Экспорт содержит ID аренды,
лот, категорию, время, статус, цену в минорных единицах и валюту. Имена и почта арендаторов
в файл не входят. К текстовым значениям, которые электронная таблица может принять за формулу,
добавляется начальный апостроф. Строки читаются курсором из отдельной транзакции с политиками
доступа организации и передаются порциями.

При проверке выгрузки из PostgreSQL сервер передал 100 000 строк (~13,7 МБ) в 392 порциях.
Самая большая порция составила 35 188 байт, замеренный прирост памяти процесса — около 3,9 МБ.

## Как воспроизвести замер

На отдельной PostgreSQL с применёнными миграциями запустите из `backend/`:

```powershell
$env:ANALYTICS_BENCHMARK_DATABASE_URL = 'postgresql://postgres@127.0.0.1:5432/keep_rollin_benchmark'
uv run --locked python -m scripts.benchmark_analytics --plans analytics-plans.txt
```

Скрипт создаёт организацию с 100 000 аренд, 500 лотами и 20 категориями и удаляет её в конце.
Прямые SQL-замеры и запросы FastAPI выполняются с ролью приложения. План включает фактическое
время, обращения к буферам и способы доступа для выбранных периодов, категорий и лотов.
Данные для отчёта вычисляются по таблицам аренды и каталога, поэтому смена статуса отражается
в следующем запросе.

## Результат на 100 000 аренд

Локальный PostgreSQL 17.11 в контейнере, окно 365 дней, 20 последовательных запросов после
пяти прогревочных для каждого сценария. Замер включает проверку доступа и сериализацию
FastAPI через HTTPX ASGITransport, без внешней сети. Порог 300 мс задан для p95.

| Сценарий | p95, мс |
| --- | ---: |
| Итоговые показатели | 1 232 |
| Выручка по дням | 1 179 |
| Выручка по категориям | 734 |
| Выручка по лотам | 2 247 |
| Выручка по дням одной категории | 457 |
| Загрузка по дням | 959 |
| Детали одного лота | 221 |
| Сравнение двух годовых периодов | 1 210 |

`EXPLAIN (ANALYZE, BUFFERS)` показал 537 мс для итогов за год, 920 мс для дневной
группировки, 3,6 мс для одного лота и 18,2 мс для семидневного окна. В семидневном запросе
PostgreSQL выбрал индекс `ix_rental_analytics_start` и `Index Only Scan`. Для годовых выборок
основная работа приходится на агрегацию большого числа строк. Миграция также добавляет
индекс по лоту и старту аренды, индекс пересечения интервалов и индекс по категории лота.

Порог для широких окон остаётся открытым. Следующий вариант оптимизации — дневные агрегаты
по лотам с обновлением при изменении аренд. Частичные дни и данные с ожидающим обновлением
следует считать по текущим строкам, чтобы сохранить точность и актуальность.
